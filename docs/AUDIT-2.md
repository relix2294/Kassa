# Аудит №2 — полный проход по коду (деньги, безопасность, инфраструктура, офлайн)

Дата: 2026-10-25. Ветка: `claude/shop-balance-notifications-7jbi4q`.
Первый аудит (`docs/AUDIT.md`, сентябрь 2026) почти весь закрыт. Этот аудит
покрывает код, добавленный ПОСЛЕ него: подотчёт («на руках»), оплаты
поставщикам из подотчёта, `paid_from`, двойные чеки, утренний размен, движение
долгов, деплой/зеркало/CI.

**Метод:** чтение всего кода (`server/src`, `web/src`, `deploy`,
`.github/workflows`, `scripts`), сверка денежных формул между модулями.
Серверный и web `tsc --noEmit` — зелёные. Денежные автотесты (`server/test`)
очень обстоятельные, но вживую в этой среде не прогонялись: не поднят Postgres.

## Главный вывод

Фундамент крепкий: разделение прав владелец/кассир выдержано, суммы не
доверяются клиенту, продажи/возвраты/приём/списание — атомарные транзакции с
блокировкой строки, идемпотентность чека реальная, денежная модель подотчёта
внутренне согласована (лента = баланс Кабинета, подтверждено тестами).

Основные риски — НЕ в бизнес-логике, а по краям:
1. **Секреты и транспорт** — токен Telegram навсегда в истории git; зеркало и
   кабинет владельца ходят по открытому HTTP; `.env` с секретами запекается в
   Docker-образ.
2. **Один логический бэкдор** — боту можно написать в личку и вытащить финансы.
3. **Устойчивость кассы к сбоям сервера (5xx)** — временная ошибка сервера
   выбивает кассира из смены и помечает очередь «проблемной».
4. **Хардёнинг инфраструктуры** — root в контейнерах, пароль по SSH,
   неатомарное восстановление БД.

## 🔴 Критично — до боевого запуска

### K1. Токен Telegram-бота навсегда остался в истории git
`deploy/docker-compose.yml` (версия до коммита `1e24f87`):
`TELEGRAM_BOT_TOKEN:-8752204018:AAHC…OegcM`. Из HEAD убран, но достаётся из
истории одной командой. Комментарий в текущем compose подтверждает: бота уже
угоняли именно из-за этой утечки.
**Эксплуатация:** любой с доступом к репозиторию берёт токен → полный контроль
над ботом (чтение группы, рассылка, перехват `/report` с выручкой).
**Чинить:** отозвать/перевыпустить токен в @BotFather (старый считать мёртвым).
Новый — только в GitHub Secrets / `deploy/.env` (для текущего кода уже так).
Историю — по возможности переписать (`git filter-repo`), либо считать токен
безвозвратно скомпрометированным (главное — отзыв).

### K2. Снимок всей базы и секрет зеркала идут по открытому HTTP
`deploy/.env.store.example` → `MIRROR_URL=http://185.18.53.234:8080/...`;
`deploy/sync/sync.sh`; приём `server/src/routes/mirror.ts`.
Каждые ~10 минут по plaintext HTTP уходит полный `pg_dump` (включая
`users.pin_hash` — bcrypt-хеши 4-значных PIN, `cost_price`, выручку, журнал) и
заголовок `X-Mirror-Secret`. Кабинет владельца на зеркале тоже по HTTP — JWT
владельца ходит открыто.
**Эксплуатация:** перехват трафика = вся база + офлайн-брутфорс PIN (4 цифры —
мгновенно); перехват `MIRROR_SECRET` → подмена базы зеркала; перехват JWT →
вход в кабинет.
**Чинить:** HTTPS/TLS для `MIRROR_URL` и доступа к зеркалу (reverse-proxy с
сертификатом, напр. Caddy/nginx + Let's Encrypt); дополнительно — приём снимков
только с IP магазина. (Сравнение секрета через `timingSafeEqual` — уже верно.)

### K3. Секреты `.env` запекаются в Docker-образ
`.dockerignore` не исключает `.env`/`deploy/.env`/`deploy/backups`, а
`deploy/Dockerfile` делает `COPY . .` с контекстом из корня репо. При каждой
пересборке `.env` (с `DB_PASS`, `JWT_SECRET`, `MIRROR_SECRET`,
`TELEGRAM_BOT_TOKEN`) и дампы БД попадают в слой образа.
**Эксплуатация:** любой, у кого есть образ (`docker save`), читает все секреты и
данные магазина.
**Чинить:** добавить в `.dockerignore`: `**/.env`, `deploy/.env`,
`deploy/backups`, `**/*.pem`. Идеально — multi-stage со сборкой web и
прод-стадией без исходников (см. V10).

### K4. Миграционный цикл в entrypoint не падает при провале
`deploy/entrypoint.sh` — до 30 попыток `npm run migrate`, при успехе `break`,
но если все провалились — нет `exit 1`. `set -e` не срабатывает (ошибку «съедает»
`if`), скрипт идёт на `seed` и `start`.
**Последствие:** если БД не поднялась за ~60 сек, приложение стартует против
неинициализированной БД и крутится полуживым; `restart: unless-stopped` не лечит.
**Чинить:** флаг успеха, после цикла `if [ -z "$ok" ]; then exit 1; fi`.

## 🟠 Высокий — заметят быстро / опасно

### V1. Бэкдор: посторонний вытащит финсводку у бота в личке
`server/src/lib/telegram.ts:581` — `allowed = chatId === String(CHAT_ID) ||
addressedToBot(text)`. Ветка `addressedToBot` срабатывает в ЛЮБОМ чате, если
текст содержит `@<имя_бота>`. Имя бота публично, режим приватности в личке не
действует.
**Эксплуатация:** посторонний пишет боту в личку `/report@<имя_бота>` → получает
`buildSummary()`: выручку, маржу, «сколько у нас денег», долги поставщикам.
**Чинить:** отвечать строго при `chatId === String(CHAT_ID)`; `addressedToBot`
оставить только как доп. фильтр ВНУТРИ нужного чата, не как основание ответа.

### V2. `/api/mirror/upload` исполняет произвольный сырой SQL
`server/src/routes/mirror.ts` — тело запроса целиком идёт в `client.query(sql)`.
По замыслу доверенный канал (защищён `MIRROR_SECRET` + ролью `mirror`), но в
связке с K2 (секрет по HTTP) это даёт доступ уровня RCE к БД зеркала (`DROP`,
подмена). Нет ограничения по IP, лимит тела 256 МБ (вектор DoS).
**Чинить:** TLS + IP-allowlist (см. K2); снизить лимит тела до реального размера
дампа.

### V3. Временная ошибка сервера (5xx) выбивает кассира из смены
`web/src/shift.ts:33-43` — `refreshShift` в ветке `else` обнуляет смену при
ЛЮБОМ статусе ошибки, не только 401/403. Транзиентный 500/503 на
`/shifts/current` (рестарт/перегрузка/деплой) → `current=null` → экран продажи
показывает «Приём кассы», кассир не может продавать.
*Нюанс:* вторую параллельную смену сервер открыть не даст
(`uniq_open_shift_per_user`), так что «расщепление сверки» ограничено; главный
вред — остановка продаж на ровном месте.
**Чинить:** обнулять смену только при `err.status === 401 || 403`; на прочих
статусах хранить последнюю известную смену, как при обрыве сети.

### V4. 5xx при отправке очереди выжигает ретраи → операции в «проблемные»
`web/src/sync.ts:187-200` — «сетью» считается только `err.status === undefined`;
любой HTTP-статус (включая 5xx) инкрементит `tries`, при `>= 5` помечает
`failed`. `flushOutbox` зовётся раз в секунду без backoff.
**Последствие:** рестарт сервера дольше ~5 сек переводит все накопленные
офлайн-чеки/возвраты в «проблемные» (ручной разбор владельцем).
*Нюанс (хорошо):* операции при этом НЕ удаляются и НЕ теряются — всплывают как
«проблемные». Это главное отличие от старой находки про молчаливую потерю.
**Чинить:** 5xx/429 трактовать как временную ошибку (как сеть: `break`, без
инкремента `tries`), добавить экспоненциальный backoff; в `failed` переводить
только по настоящим 4xx (400/409/422).

### V5. Операции «зависают» невидимо после смены пользователя на устройстве
`web/src/sync.ts:179` (фильтр по автору) + `QueuePage.tsx` (StuckBanner только
при `failed > 0`). Если кассир A в офлайне провёл чек (pending), вышел, и вошёл
B — чек A не отправляется (userId mismatch) и висит `pending` без крупной
тревоги (только бейдж «в очереди: N»).
**Чинить:** StuckBanner должен тревожить и на застрявшие `pending` (чей `userId`
≠ текущего, или старше N минут); на logout — предупреждать о неотправленных
операциях текущего пользователя.

### V6. Все контейнеры работают от root
`deploy/Dockerfile`, `deploy/sync/Dockerfile`, `deploy/backup/Dockerfile` — нет
`USER`. При RCE в Node — root внутри контейнера.
**Чинить:** непривилегированный пользователь (`USER node` + `chown` на `/app`).

### V7. Восстановление боевой БД неатомарно и сносит прод
`scripts/restore.sh` — `dropdb` живой базы, затем заливка дампа БЕЗ
`--single-transaction`/`ON_ERROR_STOP`, приложение не остановлено. README и
скрипт рассинхронизированы (README грузит в существующую `kassa`, скрипт делает
drop/create).
**Последствие:** обрыв посередине восстановления в день аварии = безвозвратная
потеря боевых данных.
**Чинить:** `psql --single-transaction -v ON_ERROR_STOP=1`; сперва
останавливать app/sync; восстанавливать в новую базу и переключать.

### V8. Деплой и workflow по SSH с паролем + TOFU
`.github/workflows/deploy.yml` и прочие — `sshpass -e ssh -o
StrictHostKeyChecking=accept-new`, секрет `VPS_PASSWORD`, часто под root.
**Последствие:** пароль слабее ключа; `accept-new` допускает MITM при первом
коннекте; утечка `VPS_PASSWORD` = весь сервер (с Marzban и прочими контейнерами).
**Чинить:** SSH-ключ вместо пароля; `known_hosts` из секрета вместо `accept-new`;
отдельный непривилегированный deploy-пользователь.

### V9. Финансовые данные выгружаются в логи GitHub Actions
`balancecheck.yml`, `tillcheck.yml`, `lowstock.yml`, `export.yml` печатают суммы,
продажи, остатки, ленту подотчёта в лог. `setup.sh`/README предлагают временно
сделать репозиторий публичным.
**Чинить:** держать репозиторий приватным всегда; вывод — в artifact с
ограниченным доступом, а не в текст лога.

## 🟡 Средний — вылезет при росте / при сбоях

### S1. Системная гонка проверок «хватает ли в кассе/на руках» (TOCTOU)
`shifts.ts` (withdraw/deposit), `expenses.ts` (расход владельца и approve),
`suppliers.ts` (`checkPaySource`) — проверка доступной суммы делается вне
транзакции обычным `query`, вставка — отдельно. Два одновременных «вывода денег»
могут оба пройти и увести ожидаемую кассу/подотчёт в минус.
*Нюанс:* переполнение по накладной защищено `FOR UPDATE`; конкуренция в
одно-магазинном сценарии (один владелец) низкая — отсюда «средний», а не выше.
**Чинить:** проверку доступности и вставку делать внутри одной `withTx` с
блокировкой (как в продаже/возврате).

### S2. Инвентаризация с `apply=true` перезаписывает остаток на посчитанный
`analytics.ts` (`/inventory`) — `FOR UPDATE` держится только на короткую
транзакцию записи, а не на весь пересчёт. Продажи во время пересчёта затираются
установкой `stock=counted`.
*Нюанс:* фронт предупреждает об открытой смене; это известное ограничение.
**Чинить:** либо блокировать продажи на время инвентаризации, либо считать
разницу от снимка остатка на момент старта пересчёта.

### S3. Скидки не покрыты проверкой `expected_price` → возможен разрыв кассы
`web/src/pages/SalePage.tsx:184` шлёт `expected_price` = обычная цена;
`server/src/routes/sales.ts:177` сверяет только `basePrice = sale_price`, а
активность акции (`:188`) пересчитывает независимо по `discount_left`.
**Сценарий:** лимит акции `discount_left` заканчивается на другой кассе между
сканом и оплатой. Касса и экран покупателя показывают акционную сумму, а сервер
проводит по полной (409 не возникает). Покупателю назвали меньше, в ящик
положили меньше, чек записан на полную — расхождение кассы. Обратный случай —
молча дешевле.
**Чинить:** передавать на сервер снимок скидки и сверять его; либо показывать
кассиру актуальную акционную цену от сервера на моменте оплаты.

### S4. `bulkPut` каталога не удаляет исчезнувшие/архивные товары
`web/src/sync.ts:30-38` — `pullProducts` только мержит. Товары,
заархивированные на сервере, пока касса была офлайн, остаются в локальном
каталоге → кассир отсканирует и продаст архивный товар.
**Чинить:** при полном pull делать реконциляцию (удалять локальные id, которых
нет в ответе) или отдельно чистить архивные.

### S5. Денежные модалки теряют введённое при клике по фону
Оплата (`SalePage.tsx:384-390`), `QtyModal`, `WeightModal`, `WithdrawModal`,
`DepositModal`, `ExpenseModal` закрываются по backdrop и сбрасывают суммы.
`ReturnPanel`/`InventoryPanel` уже защищены `useGuardedClose` — защита применена
непоследовательно, именно денежные формы без неё.
**Чинить:** обернуть в `useGuardedClose` / `stopPropagation` + явная «Отмена».

### S6. Откат остатка не делается, если отложенная продажа стала «failed»
`web/src/sync.ts:285,295` — оптимистичное списание не откатывается при переводе
операции в `failed`. Деньги не теряются (чек в «проблемных»), но локальный
остаток занижен до следующего pull.
**Чинить:** при переводе sale/return в `failed` откатывать `adjustLocalStock`.

### S7. Автологаут по 401 молча стирает набранный чек
`web/src/api.ts:26` → `logout()` → `web/src/auth.ts` чистит корзину. Протухший
токен на фоновом запросе стирает неоплаченный чек без предупреждения.
**Чинить:** не разлогинивать при непустом чеке без подтверждения; либо тихо
обновлять токен.

### S8. CORS открыт для всех источников
`server/src/index.ts:48` — `app.use(cors())` (origin `*`). Токен в Bearer (не
cookie), классического CSRF нет, но в связке с хранением токена в `localStorage`
любой XSS/чужой origin свободно обращается к API.
**Чинить:** ограничить `origin` адресом кассы/зеркала.

### S9. Нет заголовков безопасности и общего rate-limit
`server/src/index.ts` — нет `helmet`/CSP/HSTS; rate-limit только на
`/api/auth/login`. 30-дневный JWT в `localStorage` при XSS уводится надолго.
**Чинить:** `helmet` + CSP, HSTS (после TLS), rate-limit на мутирующие эндпоинты.

### S10. `NODE_ENV` не выставлен в production
`deploy/docker-compose.yml` не задаёт `NODE_ENV`, поэтому жёсткий отказ запуска
при слабом `JWT_SECRET` (`index.ts:36-45`) не срабатывает, и Express не в
прод-режиме. (Пустой секрет сейчас ловит `${JWT_SECRET:?...}` в compose, но
слабый, вписанный руками, пройдёт молча.)
**Чинить:** `NODE_ENV=production` в compose.

### S11. Слабый PIN и дефолтный владелец owner/1234
`server/src/seed.ts` (`DEFAULT_OWNER_PIN='1234'`), `auth.ts` (лимит 7 попыток/10
мин, в памяти процесса). 4 цифры = 10 000 комбинаций; счётчик сбрасывается при
рестарте. В связке с K2 (утечка bcrypt-хешей) офлайн-перебор тривиален.
**Чинить:** принудительная смена PIN владельца при первом входе; рассмотреть 6
цифр; persist-счётчик попыток в БД.

### S12. Нет HEALTHCHECK, `depends_on` без условия
`deploy/docker-compose.yml` — ни одного `healthcheck`; `depends_on: - db` без
`condition: service_healthy`. Эндпоинт `/api/health` есть, но Docker его не
опрашивает. Зависший app не перезапускается; app может стартовать раньше БД.
**Чинить:** healthcheck на app (`curl /api/health`) и db (`pg_isready`) +
`depends_on: condition: service_healthy`.

### S13. Одностадийная сборка: dev-инструменты и исходники в прод-образе
`deploy/Dockerfile` — один `FROM`, `npm install` с dev-зависимостями, `COPY . .`,
`start` гоняет TS через `tsx` в проде. Большой образ, лишняя поверхность,
исходники целиком внутри.
**Чинить:** multi-stage (builder + прод-стадия), либо `npm ci --omit=dev` после
сборки.

## 🔵 Низкий / информационно

- **L1. ROLE по умолчанию `store`** — если на VPS забыли `ROLE=mirror`,
  `/api/mirror/upload` молча отдаёт `not_a_mirror`, синхронизация тихо не
  работает. Чинить: алерт при серии неуспешных отправок в `sync.sh`.
- **L2. Образы не запинены по digest** (`node:20-slim`, `postgres:16-alpine`) —
  невоспроизводимость пересборки. Запинить `@sha256:...`.
- **L3. Диагностический шаг деплоя печатает IP сервера и длину пароля**
  (`deploy.yml`). Сами секреты не светятся, но метаданные лишние.
- **L4. `tillzero.yml` не идемпотентен** — прямой `INSERT` закрытой смены, повтор
  добавит вторую нулевую смену.
- **L5. Ротация бэкапов по возрасту (`-mtime`), а не по количеству** — при
  интервале < суток число файлов не ограничено (при дефолте раз в сутки — ок).
- **L6. WS не перепроверяет `is_blocked`** при подключении (`realtime.ts`):
  заблокированный кассир с живым токеном продолжает получать события
  `audience:'all'` (только каталог без `cost_price`). Влияние низкое.
- **L7. `STORE_TIMEZONE` подставляется в SQL строкой** (`dashboard.ts`,
  `export30.ts`, `telegram.ts`). Значение из env оператора — инъекции нет, но
  лучше `AT TIME ZONE $1` или валидация по whitelist.
- **L8. Деньги как JS-float** (`db.ts` `parseFloat`; `cart.ts`/`PaymentForm.tsx`).
  Смягчено: суммы считает SQL (numeric), на клиенте только отображение, везде
  `toFixed(2)`, сервер пересчитывает итог по позициям. Латентный класс, не баг.
- **L9. Старые чеки `mixed` до миграции `cash_amount`** — `COALESCE(cash_amount,
  total)` засчитает весь total как наличные (бэкфилл заполнил только чистый
  cash/card). Касается лишь старых уже закрытых смен.
- **L10. `export30` для «пора закупить» использует только `stock < LOW`**,
  игнорируя индивидуальный `min_stock` (в отличие от `/analytics/restock`).
  Мелкая несогласованность единого правила.
- **L11. Нет версионирования миграций** — `migrate.ts` прогоняет весь

## Надёжность / SPOF

- Данные переживают рестарт/краш/пересборку: БД в named volume `kassa-db`,
  бэкапы в bind-mount (но НЕ `down -v`). `restart: unless-stopped` на всех.
- Нет репликации БД; бэкапы лежат на том же хосте, что база (оффсайт — только
  зеркало, и то по HTTP, K2). Потеря/компрометация VPS-пароля (V8) = потеря
  всего.
- Направление синхронизации безопасно: строго магазин→зеркало, зеркало read-only
  (`index.ts:59-64`), снимок накатывается в одной транзакции (`mirror.ts`).

## Что сделано хорошо (проверено, не выдумано)

- Разделение прав владелец/кассир выдержано на уровне роутеров и эндпоинтов;
  `user_id` берётся из токена, не из тела.
- `cost_price`/маржа последовательно режутся кассиру в API и в WebSocket.
- Все запросы к БД параметризованы; строковые интерполяции — только whitelisted
  (`sortBy`, `bucket`, `field`) или серверные константы.
- Продажа/возврат/приём/списание/инвентаризация — транзакции с `SELECT … FOR
  UPDATE`; оверселл заблокирован атомарно.
- Идемпотентность чека: unique `client_id` + обработка `23505`; покрыта тестом на
  одновременную двойную отправку.
- `shift_id` фиксируется на момент продажи, не отправки; поздний чек в закрытую
  смену пересчитывает сверку (`late_sale`).
- Денежная модель подотчёта согласована: лента (`ledger.ts`) = баланс Кабинета
  (`dashboard.ts`) = CLI, расход «из подотчёта» не считается дважды — всё покрыто
  тестами.
- Бэкапы: `pg_dump` + `gzip -t` + проверка на пустоту + атомарная запись
  `.part`→`mv` + ротация.
- `timingSafeEqual` для секрета зеркала; rate-limit на вход; порт БД наружу не
  публикуется; токен Telegram в деплое передаётся по stdin (в логах только длина).

## Рекомендуемый порядок

1. **Секреты/транспорт (до любого боя):** отозвать токен бота (K1); HTTPS для
   зеркала и кабинета (K2); убрать `.env` из образа (K3); закрыть бэкдор бота (V1).

   атомарное восстановление БД (V7).

   видимость застрявших чеков (V5).
4. **Хардёнинг:** non-root контейнеры (V6); SSH-ключи вместо пароля (V8); финансы
   не в логи Actions (V9); `NODE_ENV=production` (S10); healthcheck (S12).
5. **Целостность денег/склада:** гонки проверок кассы (S1); скидка vs
   `expected_price` (S3); реконциляция каталога (S4).
