# ТЗ на MVP — программа учёта для магазинчика

## 1. Суть
Веб-программа для маленького магазина (10–40 м²). Задача: каждая продажа
пробивается, склад считается сам, владелец видит всё в телефоне в реальном
времени. Ценность для владельца — перестать зависеть от того, что за кассой
обязательно родственник, и иметь возможность нанять обычного сотрудника без
страха.

## 2. Границы MVP — чего НЕ делаем
- Не пробиваем фискальные чеки в налоговую. Только внутренний учёт.
- Один магазин = один аккаунт. Мультиточечности нет.
- Поштучный/весовой товар без штрихкода (курут и т.п.) — не в MVP.
- Полного офлайн-режима нет (см. п. 8 — есть локальное хранение + синхронизация).
- Своего железа нет. Магазин использует свой ноут + сканер + опционально термопринтер.
- Мобильного приложения нет. Только веб в браузере.
- Нет бухгалтерии, зарплат, налогов, интеграций с банками.

## 3. Устройства
- Касса: ноутбук/ПК + сканер штрихкодов (обязательно), термопринтер опционально.
- Владелец: смотрит с телефона через браузер.
- Один продукт, разные экраны под роль.

## 4. Роли и права
**Владелец** — видит всё: продажи в реальном времени, выручку, маржу,
закупочные цены, остатки, аналитику, логи. Управляет товарами и ценами.
Заводит и блокирует кассиров.

**Кассир** — процесс продажи и (по настройке) приём товара. НЕ видит закупочные
цены, общую выручку и маржу. НЕ меняет цену продажи. НЕ удаляет чек бесследно.
НЕ видит чужие смены. Открывает и закрывает свою смену.

Приём товара по умолчанию доступен обоим.

## 5. Экраны

### Продажа (касса)
Скан штрихкода → товар падает в чек, количество и сумма считаются. Цифровая
клавиатура для количества и сдачи. Оплата: наличные / карта. Товара нет в базе —
продать нельзя (правило: сначала приём, потом на полку). Возврат/обмен —
возможен, товар возвращается на склад, деньги выходят из кассы, операция пишется
в лог. Отмена позиции — пишется в лог.

### Приём товара
Скан штрихкода пришедшего товара → ввод количества и закупочной цены → остаток
растёт автоматически. Новый товар заводится тут же: скан → название подтягивается
из внешней базы штрихкодов → владелец вводит цену продажи и закупочную.

### Кабинет владельца (телефон), онлайн
- Продажи сейчас / сегодня / за период — выручка и маржа.
- Остатки по всем товарам.
- Раздел «Пора закупить» — где остаток ниже минимума.
- Раздел «Залежалый товар» — что долго лежит и плохо продаётся.
- Лог: отмены, возвраты, ручные операции, смены, расхождения по кассе,
  изменения карточек и цен (с указанием кто и когда).

### Смена
Кассир открывает и закрывает смену. Система считает «сколько должно быть в кассе
по чекам» и сравнивает с фактически сданным. Расхождение видит владелец.

## 6. Склад
- Продажа списывает, приём добавляет. Остаток = приход − продажи.
- Себестоимость — средняя скользящая (при каждом приёме пересчитывается средняя
  закупочная цена). Не партионный учёт.
- У каждого товара — поле «минимальный остаток» (для раздела «Пора закупить»).
  Настройка порогов в интерфейсе — позже.
- Один штрихкод на товар (ранний кандидат на доработку).
- Инвентаризация: владелец считает реальный остаток, система показывает недостачу
  (по товару, периоду, смене).
- Массовая смена цен — по одному товару и по категории.

## 7. Логирование (продукт построен на прозрачности)
Пишется с указанием пользователя и времени: продажи, отмены, возвраты,
открытие/закрытие смены, расхождения по кассе, изменения карточек товара,
изменения закупочных и продажных цен.

## 8. Данные и надёжность
- Истина живёт локально на компе кассы. Раз в секунду данные зеркалируются на сервер.
- Сервер = бэкап + источник для кабинета владельца.
- Кабинет владельца показывает состояние на момент последней синхронизации кассы
  (при работающей кассе и сети — те же секунды).
- Короткий обрыв сети не должен терять открытый чек и вешать кассу.
- Бэкап данных — обязанность с первого дня, не фича.

## 9. Порядок разработки
1. Товары + склад + приём.
2. Продажа со сканером + списание.
3. Роли и права.
4. Смена + сверка кассы.
5. Кабинет владельца в реальном времени.
6. Аналитика: «пора закупить» и «залежалый товар».

Аналитика последней — она работает только на чистых данных из пунктов 1–5.

## 10. Открытые риски (держать в поле зрения, не в MVP)
- Внешняя база штрихкодов — надо проверить, что местные таджикские товары в ней
  есть. От этого зависит скорость первого запуска. Требует отдельной проверки.
- Первый завод 2000 товаров — самый вероятный момент, где клиент бросит. Модель:
  владелец заводит сам + консультант рядом. Живучесть зависит от скорости
  заведения (скан + автоназвание + только цена руками).
- Один штрихкод на товар и ручные пороги минимума — вернутся как запросы от
  клиентов рано.
